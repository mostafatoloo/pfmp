# Internationalization (Phase 2)

English is the **only enabled production language**. The architecture is multilingual-ready (including RTL).

## Package

`@pfmp/i18n` provides:

- Locale registry (`LOCALES`, `enabledLocales`, `resolveLocale`)
- Namespaced English message catalogs (`messages/en/*`)
- `createTranslator` / `useT` with interpolation, plural key suffixes (`_one` / `_other`), and missing-key logging
- Safe fallback to English
- Locale-aware formatting helpers (dates, numbers, durations, relative day keys)
- Direction via locale config (`ltr` / `rtl`) and logical CSS in the design system

## Adding a new language

1. Add a `LocaleDefinition` in `packages/i18n/src/locales.ts` with `enabled: false`.
2. Copy `packages/i18n/src/messages/en/` to `messages/<code>/` and translate strings.
3. Register the catalog in `translate.ts` (`registerCatalog` / catalogs map).
4. Translate every key; run unit tests and a missing-key scan in development.
5. Verify RTL (if applicable) with layout checks — use `PFMP_FORCE_RTL=1` for English+RTL simulation without enabling an unfinished locale.
6. Set `enabled: true` only when translations and QA are complete.
7. Do **not** expose unfinished languages in the settings selector (`enabledLocales()`).

## Distinct concepts

| Concept | Source |
|---------|--------|
| UI language | `User.locale` / enabled locale registry |
| Text direction | Derived from locale definition |
| Time zone | `User.timezone` |
| Calendar system | `User.calendarSystem` (`gregory` \| `persian`) — independent of language |

## Dev RTL simulation

```bash
PFMP_FORCE_RTL=1 pnpm dev
```

Uses English messages with `dir="rtl"` so layout can be tested without shipping Persian UI copy.
